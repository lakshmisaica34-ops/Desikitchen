

## Stage 0 — Authentication: impersonating the browser, not using an API There is no API for saved posts (Instagram has never offered one), so everything runs on the user's own session cookie against the private web endpoints the Instagram web app itself calls. iglib.mjs is the shared client and contains the trick that makes it work: - Cookie comes from the env (Instagram_cookie), must contain sessionid=, and the csrftoken= is parsed out of it and sent as x- csrftoken. - The headers are a UA ↔ sec-ch-ua consistency pair: a Chrome 148 UA string plus matching sec-ch-ua, sec-ch-ua-full-version-list, sec-ch- ua-platform etc., plus x-ig-app-id: 936619743392459 (the official web app id) and x-asbd-id: 359341. Instagram gates the JSON API behind this "useragent mismatch" check — if the UA and the client hints don't describe the same Chrome build, you get bounced to the HTML/ shield path. With a matched pair you get clean JSON. - redirect: 'manual' is deliberate: a 302 means the session is walled, and the caller treats non-200 as "stop, state is saved". - saved.mjs additionally carries the x-ig-www-claim header, refreshing it from x-ig-set-x-www-claim on each response — that's Instagram's request-claim token, and failing to round-trip it is another way to get challenged. There is also ia_src/, a Python variant (InstagramClient → SavedScraper / ProfileScraper) that does the same job but reads cookies directly out of the installed browser profile (browser='chrome', profile='Default' via yt_dlp_utils.setup_session), adds a SQLite dedup log (.log.db, save()/is_saved() per URL), and fans the work into async image/video/ comments workers. It's the polished library version; the .mjs scripts are the ones the measured pipeline actually used. ─────────────────────────────────────────────────────────────────────── 

## Stage 1 — Discovery: paging the saved feed fetch_video_urls.mjs (and its cousins saved.mjs, bfs_saved.mjs) enumerate the collection. - Endpoint: GET /api/v1/feed/collection/<COLLECTION_ID>/posts/ — ~30 posts per page. - Pagination: each response's next_max_id becomes ?max_id=… on the next request, and is written to work/video_urls_state.json after every page. Output goes append-only to work/video_urls.jsonl. - On startup it reloads both: every code already in the output goes into a seen set, and the cursor is restored — so it resumes mid- collection exactly where it stopped. - Politeness: sleep(2200 + random*1800) between pages (~400 requests/ hour max), and on 429/400/network it does exponential backoff 120s → 1800s cap and retries the same page instead of skipping it. - bfs_saved.mjs was the reconnaissance tool: it parses the saved page's rsrcMap, walks the JS chunk graph breadth-first, downloads each chunk with curl, and greps for params:{id:"…",name:"Saved…Bookmark…"} — that's how the GraphQL doc_ids and the collection id were discovered in the first place. - Each item is normalised through compact(): only id, code, username, caption, media_type, product_type, like/comment counts, taken_at, video_duration, accessibility_caption, location, saved_collection_ids, video_urls are kept. Everything else is dropped at the door. ## Stage 2 — Classification + caption extraction (the free pass) pipeline/caption_extract.mjs on Groq's free tier (openai/gpt-oss-120b), over exports/recipe_scrape_results_final.json. One prompt does two jobs (flag --mode classify vs full): - A) food_post — is this about making/presenting food? (a dish name + recipe hashtags is true; ads, fitness, restaurant tours, "someone eating" are false) - B) completeness of the caption alone: full (ingredients and usable method) / partial (one half) / none (name + hashtags only) - C) dish, dish_en, language (en, te, hi, mr, …), reason - D) only if full/partial: extract ingredients[{item, quantity, item_en}] + steps + steps_en, with hard anti-hallucination rules — "

### Never invent ingredients, quantities, times or steps. If none, use [ ]." Quantity is copied exactly as written, original language preserved for item/steps, English only in the _en fields. Operational properties: - Output work/caption_results.jsonl is append-only and deduped by code (loadDone() skips anything already present and not error). - It's quota-aware: --from/--to/--limit slice the run, and it stops cleanly when the daily/per-minute token budget runs out so another runner can pick up the remainder. - Priority ordering (FULL → METHOD_ONLY → ING_ONLY → EMPTY → NONE) processes the highest-value captions first, so a truncated run still yields the most recipes. - work/caption_cost.json records model, tokens, API seconds, and the needs_video count — that number is the input to stage 4. Earlier/parallel paths in the same tier: run_recipe_scrape.mjs (pure heuristic, zero LLM: keyword scan of caption → keyword scan of top comments → NOT_RECIPE, never touches video) and fetch_comments.mjs ( top-level comments via /api/v1/media/<pk>/comments/, then re-classify from what commenters wrote — often the creator posts the full list in a pinned comment). ─────────────────────────────────────────────────────────────────────── 

## Stage 3 — Merge and build the video queue pipeline/build_dataset.py reconciles all caption sources: 1. Loads caption_results.jsonl + any batch outputs + the heuristic audit categories. 2. normalize() enforces shape: drops non-dict ingredients, blanks quantity, forces steps/steps_en to equal length (truncating to min( len) so translations can never desync), and demotes a full claim to partial unless both ingredients and steps actually came back — the model's self-assessment is not trusted. 3. If multiple engines produced a row for the same code, the one with the higher score() wins (ings + 2*steps), so richer extractions beat poorer ones. 4. Emits work/caption_merged.jsonl (validated rows) and work/ video_queue.jsonl = every post that is a food post and not full — i. e. exactly the reels that still need their pixels read. ─────────────────────────────────────────────────────────────────────── 

## Stage 4 — The video pass: frames + audio instead of video This is where the cost engineering lives (pipeline/ video_extract_stills.mjs, current) with video_extract.mjs (whole-video) kept as fallback. Why stills: Gemini bills ~258 tokens per second of video regardless of resolution or fps. A 50 s reel costs ~$0.002 as video but ~$0.001 as 10–12 stills — with the same ingredient recall. Per reel: 1. URL — take the CDN URL pre-fetched in stage 1 from the in-memory Map; media-info only as a last resort (serialised, rate-limited — see the spam flag above). 2. Frames — ffmpeg -skip_frame nokey -vf scale=512:-2 -vsync vfr -q:v 3 f%03d.jpg. Instagram GOPs are ~5 s, so decoding only keyframes gives the same spacing as fps=1/5 for ~1/6 of the CPU (6.9 s vs 20.3 s per reel). This was measured as the single biggest speed win. 3. Audio — -vn -ac 1 -ar 16000 -b:a 32k to a 32 kbps mono MP3, because much of the recipe is spoken. 4. Streaming overlap — the CDN files are faststart (moov before mdat), so the download is piped straight into ffmpeg (pipe:0) and keyframe decode overlaps the network transfer; extraction pops the moment the last byte arrives (14 s → 9 s per reel). STILLS_STREAM=0 reverts to download-then-extract. 5. Send — OpenRouter → google/gemini-2.5-flash-lite, message parts = [{ type:'image_url', data:image/jpeg;base64,…} × N, {type: 'input_audio', format:'mp3'}] plus the caption. The prompt ( STILLS_EVERY=4, STILLS_MAX=30, STILLS_SCALE=512) says: read the frames in order plus audio, return strict JSON only, is_recipe / dish / dish_en / language / ingredients / steps / steps_en / serves / time / confidence / notes, with the same never-invent rule and the explicit notes that a silent visual cook-through IS a recipe and steps must be one language, one entry each, same length as steps_en. 6. Persist — append to work/video_results.jsonl; failures go to work/ video_errors.jsonl for the next run; work/video_log.csv records per- video download_s, encode_s, api_s, total_s, bytes, tokens, USD — the cost ledger that proves each method is worth it. 7. Parallelism — node pipeline/video_extract.mjs [workers], bounded, since the bottleneck is link bandwidth (~5 MB/s aggregate), and prefetching the next download was measured not to help. Quality check that shaped the design: on 18 reels with both passes, keyframes recover 84% of the full-video ingredient list (149/177); re- running at 720 px changed nothing (same tokens, same recall) → the gap is temporal, not resolution. 42 frame-pass results came back thin (<4 ingredients), so those were re-run as full video for $0.0703 total, taking 102 → 199 ingredients (mean 2.4 → 4.7/reel). That "targeted re- read of thin results only" is the economical fix, and it's why video_extract.mjs still exists. ─────────────────────────────────────────────────────────────────────── 

## Stage 5 — Merge, dedupe, build the dataset pipeline/build_dataset.py + pipeline/build_site.py: - Caption row and video row for the same code are combined: merge_ingredients() unions by normalised English item name, preferring entries that carry a quantity; if the video produced steps they replace the caption's, otherwise the caption's are kept. The chosen source becomes caption video stills. - Dedup across videos: norm_key() normalises a dish name — NFKD, strip combining marks, drop possessives (amma's → amma), keep Devanagari range, drop stopwords, singularise words >3 chars. Records with the same normalised key collapse into one card with variants[] holding every other source video (all permalinks kept). Records with no dish name at all are dropped as noise. - source: video wins for the metadata that matters (title, steps), and patches (ing_patch, title_patch) can override specific codes. - Outputs: docs/recipes.json (1,047 recipes from 1,161 source posts, 80 duplicate groups), docs/recipes.csv, docs/costs.json, docs/summary. json — and every recipe keeps the creator's original wording and the English rendering of name/ingredients/steps.
